# Источник Тем — тренды Wordstat плюс ручное предложение

Рассматривали чистый автоподбор (модель сама придумывает Темы по Нише), бэклог идей от команды, или гибрид. Выбрали два равноправных входа в План: (1) автоматический — модель предлагает Темы на основе растущих запросов Wordstat в рамках Ниши (используем уже подключённый Yandex Search API), с проверкой на повтор против истории уже сделанных Тем; (2) ручной — любой участник команды (Владелец или Контент-менеджер) может напрямую предложить свою Тему, которая идёт в План без автоподбора, но всё ещё проходит стандартную адаптацию под все Площадки. Чистый автоподбор без привязки к трендам отвергли — не даёт содержательного контроля над темами; выделенный бэклог как отдельная сущность отвергли как избыточный — ручное предложение решает ту же задачу проще.

## Уточнение по реализации (проверено живым вызовом API, 2026-08-07)

Ранее здесь была оговорка о том, что настоящей динамики частот не построить на MVP — это оказалось неверным предположением, основанным на неполной реализации `KeywordStats` (#3), а не на реальном ограничении API. Живая проверка `POST /v2/wordstat/dynamics` подтвердила: Yandex Search API отдаёт помесячную/понедельную динамику частоты по фразе (`results[]` с `date`/`count`/`share`) напрямую. См. `docs/integrations/yandex-search-api.md` за подтверждённой схемой пяти методов Wordstat.

Соответственно "растущие запросы" в `generate_plan` (#6) реализуются через настоящую динамику (`GetDynamics`), не через seed-список высокочастотных ключей "сейчас". См. issue на исправление `KeywordStats` — текущая реализация #3 обращается к неверному эндпоинту/методу/полям и на проде всегда возвращает пустой результат.

Ручной путь (2) в #6 не реализуется — это отдельная точка входа в `Plan.create`, ей нужен отдельный UI/команда в боте (см. issue про ручное предложение Темы).
