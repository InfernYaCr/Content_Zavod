# Кодек callback-данных типизирован по форме id, а не по каждому Действию

Тринадцать публичных функций (общая пара `encode`/`decode` плюс одиннадцать обёрток под отдельные Действия) схлопнуты в одну пару `encode_callback_data`/`decode_callback_data` в новом модуле `telegram/callback_codec.py`. Типизированный `dataclass` завели только для пяти Действий, которые упаковывают больше одного поля в id (`Page`, `HistoryWeek`, `HistoryVersions`, `HistoryVersion`, `ExportArticle`) — именно там ручная `rpartition`-распаковка сегодня даёт шанс перепутать порядок или число полей. Оставшиеся пятнадцать Действий несут один непрозрачный id и идут через общий `SimpleAction(action: Action, id_: str)`.

Рассматривали оба крайних варианта и отвергли оба. Типизировать все двадцать Действий отдельным dataclass'ом каждое — пятнадцать из них выродились бы в class с единственным полем `id_: str`, boilerplate ради единообразия, которое некому использовать: ни один вызывающий код не путает эти пятнадцать местами сегодня. Оставить payload полностью общим (`Action` + позиционный `tuple[str, ...]`) тоже отвергли — это и есть протекание структуры id через отсутствие типов, от которого прямо предостерегало тело тикета: кодек по-прежнему прячет разделитель и лимит в 64 байта, но какая позиция что значит для конкретного Действия остаётся знанием вызывающей стороны, не проверяемым компилятором.

Поле `action: Action` осталось только у `SimpleAction` — пять составных типов самотождественны через класс, `.action` у них было бы полем без единого читателя. По той же причине ролевой гейт в `bot.py` и `PlanReview.handle_action` не тронуты: оба по-прежнему ветвятся по `SimpleAction.action`-строке в точности как раньше. Редизайн этой ветки сознательно оставлен кандидату 05 (ролевой гейт из обзора архитектуры), который на момент этого решения ещё не прошёл свой грилинг — расширять периметр тикета #61 в его сторону не стали.
