# Версионные миграции вместо schema-on-startup

Каждый модуль накатывал свой `schema.sql` через `ensure_schema()` при старте `bot`/`worker` — работало, пока схема только росла через `IF NOT EXISTS`. Упёрлось на `plans_one_pending_review_per_week_key` (#71): партиальный уникальный индекс на «не больше одного `pending_review` Плана на неделю» накатывался вслепую, а на существующей установке с дублями это уронит старт процесса.

Вместо Alembic — который тянет SQLAlchemy engine в кодовую базу, целиком построенную на `asyncpg` и голом SQL — завели свой `MigrationRunner` (`src/content_zavod/migrations/`): пронумерованные `.sql`-файлы в `migrations/sql/`, применяются по имени файла, факт применения — в таблице `schema_migrations`, каждая миграция — в своей транзакции вместе со своей строкой в `schema_migrations`, так что упавшая на середине миграция не считается применённой и накатится заново при следующем запуске. И `bot.py`, и `worker.py` вызывают `run_migrations(pool)` один раз при старте, до создания Membership/Plan/JobQueue/... — сами модули больше не знают про свою схему.

Оба процесса стартуют независимо, так что обычный деплой (рестарт bot и worker одновременно) — это два раннера, гоняющихся за одной базой. `run_pending` держит Postgres advisory lock на весь свой прогон: второй раннер блокируется на старте, пока первый не отпустит лок, а не падает на дубликате PRIMARY KEY в `schema_migrations` (тест — `test_concurrent_run_pending_does_not_race_on_the_tracking_insert`).

## Baseline и апгрейд — одна и та же схема

`0001_baseline.sql` — это то, что раньше было пятью отдельными `schema.sql` (access, scheduling, job_queue, owner_settings, domain), один в один: `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`. Идемпотентность здесь не техническая деталь, а то, что делает существующие таблицы валидным baseline: на пустой базе это разворачивает схему с нуля, на существующей установке — no-op, и обе сходятся к одной и той же схеме. Единственное, что `0001` намеренно не включает — `plans_one_pending_review_per_week_key`: на установке с уже накопленными дублями `pending_review` Планов эта миграция бы просто упала.

`0002_dedupe_pending_review_plans.sql` архивирует все Планы кроме самого нового `pending_review` на неделю (`plans`+`plan_items`, тем же способом, каким `Plan.request_replacement` уже архивирует вытесненный План) и только после этого создаёт индекс. Тест `test_upgrade_dedupes_pre_existing_duplicate_pending_review_plans` (`tests/migrations/test_runner.py`) воспроизводит ровно этот сценарий: применяет только `0001` к копии схемы, руками вставляет два `pending_review` Плана на одну неделю (то, что стало возможно только потому что индекса ещё нет), потом прогоняет `run_pending()` и проверяет, что апгрейд не падает, а дедуп и индекс появляются.

## Rollback

Откат `0002` — `DROP INDEX plans_one_pending_review_per_week_key;` и `DELETE FROM schema_migrations WHERE version = '0002_dedupe_pending_review_plans'`. Заархивированные дубли остаются `archived` — это не потеря данных (сами Планы и их Темы никуда не делись, они просто больше не `pending_review`), и это осознанное решение: автоматически возвращать их обратно в `pending_review` при откате означало бы молча решать за оператора, какой из дублей теперь снова канонический для недели, а это именно то неоднозначное состояние, ради которого дедуп и потребовался.

Откат `0001` не предусмотрен — это baseline, откатывать существующие таблицы некуда.

## Rollout order

Expand schema → deploy code → backfill → contract schema:

1. **Expand**: `run_migrations(pool)` при старте применяет `0001`/`0002` — новые объекты появляются, старый код (без миграций) продолжает работать, потому что `0001` идемпотентен, а `0002` только архивирует дубли и добавляет индекс, не убирая ничего, от чего зависит старый код.
2. **Deploy code**: выкатывается код, который читает/пишет по новой схеме (в этой миграции — сам вызов `run_migrations` вместо `ensure_schema()`).
3. **Backfill**: `0002` совмещает backfill (дедуп) с expand-шагом, потому что backfill здесь — предусловие для безопасного добавления индекса, а не отдельная операция после деплоя.
4. **Contract**: следующая миграция, которая уберёт из схемы что-то, от чего больше никто не зависит — только после того, как expand и deploy подтверждены в проде.

Удаление старых `schema.sql`-файлов и `ensure_schema()` этим PR — не DB-level contract-шаг из списка выше: это source-level cleanup внутри одного деплоя (bot и worker в этом релизе одновременно переходят на новый код, старого code path, читающего `schema.sql`, после раскатки этого PR больше нет нигде). Contract относится к самой схеме (колонки/таблицы/constraints), которые могли бы понадобиться предыдущей версии кода во время rolling deploy — здесь такого шага пока нет: `0001`/`0002` только добавляют.

Каждая будущая миграция, добавляющая новую схему (outbox канонического сообщения, provenance/cost — см. #71's "блокирует"), следует этому же runner'у и той же последовательности.
