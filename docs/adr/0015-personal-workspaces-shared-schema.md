# Личные Пространства: общая схема с `workspace_id`, без Ролей и группового чата

Бот обслуживал одну команду: один набор Настроек (`owner_settings`), один чат доставки (`TELEGRAM_NOTIFY_CHAT_ID`), allowlist `members` с двумя Ролями и заявками на доступ, одно Расписание, один каноничный План на неделю (ADR-0005). Владелец проекта решил (#118): бот открыт любому, кто нажал `/start`; у каждого своё **Пространство** — свои Настройки, Планы, Статьи, История, Расписание и расход; работа только в личке с ботом; приглашений коллег и групп нет; доступ ограничен пробным **Лимитом**; оплаты нет, но **Учёт расхода** ведётся сразу; **Глобальный администратор** (telegram id в env) видит Пространства, их расход и поднимает Лимит; текущие данные не переносятся.

Это поток C (C0–C2, C5–C6) из `docs/plans/2026-08-12-technical-hardening-and-saas.md`, урезанный до личных Пространств: без приглашений, оплаты и web-панели. План реализации — `docs/plans/2026-10-12-personal-workspaces.md`.

## Модель данных: общая схема, `workspace_id` в каждой строке

Одна база, одна схема, у каждой пользовательской строки — `workspace_id BIGINT NOT NULL REFERENCES workspaces`. Отдельные схемы или базы на Пространство отвергли: при сотнях пробных Пространств это сотни прогонов `MigrationRunner` (ADR-0013) и пулов соединений ради изоляции, которую тот же `WHERE workspace_id` даёт дешевле. Postgres RLS тоже отвергли на этом этапе: приложение ходит в базу одной ролью-владельцем таблиц (RLS для неё нужно форсировать) через пул `asyncpg`, где большая часть запросов вне явной транзакции. Пришлось бы перед каждым запросом делать `SET LOCAL app.workspace_id`. Вернёмся к RLS, если появится второй потребитель базы (web-панель C4).

### Таблица `workspaces`

```sql
CREATE TABLE workspaces (
    id BIGSERIAL PRIMARY KEY,
    owner_telegram_id BIGINT NOT NULL UNIQUE,  -- одно Пространство на человека
    owner_username TEXT,                       -- только для показа Глобальному администратору, обновляется на /start
    timezone TEXT NOT NULL,                    -- IANA; при создании — APP_TIMEZONE
    plan_limit INT,                            -- NULL = TRIAL_PLAN_LIMIT из конфига
    article_limit INT,                         -- NULL = TRIAL_ARTICLE_LIMIT из конфига
    bot_blocked_at TIMESTAMPTZ,                -- Telegram ответил 403: пользователь заблокировал бота
    last_job_claimed_at TIMESTAMPTZ,           -- для честной очереди воркера
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- **Отдельного `chat_id` нет.** У личного чата Telegram `chat.id` совпадает с id пользователя (код уже на это опирается: `input_prompt._is_private`). Доставка идёт на `owner_telegram_id`. Отдельный chat id понадобится, только если Пространство начнёт доставлять в канал или группу, а это вне решения Владельца проекта.
- **`id` — короткое число, а не uuid,** как у Планов: его вводит Глобальный администратор (`/admin limit 12 2 12`). Пользователь `id` своего Пространства не вводит нигде, поэтому перебор чужих id ничего не даёт.
- **Лимит хранится как `NULL` = «по конфигу».** Изменение `TRIAL_*` в env сразу действует на всех, кому Глобальный администратор не задал своих чисел.
- Пространство не удаляется: удаление и экспорт данных — C5, вне этого решения. Поэтому все FK по умолчанию `RESTRICT`, без `CASCADE` (исключение — уже существующий каскад `topic_research → plan_items`).

**Составные FK** — главная страховка на уровне базы. Тема не может принадлежать Плану другого Пространства. Статья не может ссылаться на чужую Тему. Шаг Учёта расхода не может ссылаться на чужую Задачу. Ошибка в коде, которая перепутает `workspace_id` у родителя и потомка, упадёт на `INSERT`, а не тихо смешает данные.

**Правило для уникальных ключей.** Ключ по *естественному* значению всегда включает `workspace_id`: неделя (`week_label`), ключ идемпотентности, имя Настройки. Иначе два Пространства конфликтуют. Например, у обоих `generate_plan:2026-W42`, и второе получило бы `JobId` первого. Ключ по *суррогатному* id, который сам принадлежит ровно одному Пространству через составной FK, `workspace_id` не повторяет: `articles (plan_item_id, platform)`, `article_versions (source_job_id)`. Там уникальность и так в пределах Пространства, а лишняя колонка в индексе ничего не защищает.

### Tenant context в коде: явный параметр, проверяемый тестом

В проекте нет type checker'а (CI — `ruff` и `pytest`), поэтому `NewType` сам по себе ничего не гарантирует. Решение из двух частей:

1. **`workspace_id: WorkspaceId` — первый обязательный параметр каждого метода репозитория** с пользовательскими данными: `Plan`, `Article`, `GenerationSteps`, `TopicResearchStore`, `WorkspaceSettingsStore` (бывший `OwnerSettingsStore` для Настроек), `ScheduleSettings`, `PendingInputs`, публичные методы `JobQueue` (`enqueue`, `get_job`, `get_status`, `retry`). Без значения по умолчанию и без `Optional`. Связанный объект вида `plan.scoped(ws)` отвергли: он меняет форму всех сервисов Telegram-слоя, которые держат `plan`/`article` с момента старта, а параметр — механическая правка того же объёма, и его видно в каждой строке вызова.
2. **Статический тест `tests/test_tenant_sql.py`**. Он обходит строковые литералы с SQL в модулях-репозиториях. Каждый `SELECT`/`UPDATE`/`DELETE`, затрагивающий таблицу с `workspace_id`, обязан упоминать `workspace_id`. Исключения перечислены поимённо в самом тесте: системные операции очереди (`claim_next`, `heartbeat`, `complete`, `fail`, `recover_stuck`, `claim_notification`, `mark_notified`, `reschedule_notification` — они работают по `id` + `lease_token` уже захваченной Задачи), планировщик Расписания и модуль Глобального администратора `workspaces/admin.py`. Это единственные места с выборками поверх всех Пространств.

Откуда берётся `workspace_id`:

- **Бот**: из `from_user.id` входящего апдейта. Один резолв на апдейт (`Workspaces.get_by_owner`, при `/start` — `get_or_create`) превращает его в объект `Workspace` (id, owner id, tz, Лимит). Дальше объект передаётся вниз так же, как сейчас передаются `chat_id`/`user_id`. **Из `callback_data`, текста или payload `workspace_id` не берётся никогда.**
- **Воркер**: из колонки `jobs.workspace_id` захваченной Задачи. `ClaimedJob` и `JobResult` несут `workspace_id`. Хендлер получает его отдельным аргументом, а не из payload.
- **Уведомления**: из `JobResult.workspace_id`. Чат доставки — `owner_telegram_id` этого Пространства.
- **Страница для чтения**: подвал со ссылкой Проекта (`TelegraphPublisher(footer_link=...)`) сейчас — функция без аргументов, читающая единственные Настройки. Она получает `workspace_id` Статьи. Иначе Страница Статьи B вышла бы со ссылкой Проекта A. Сам telegra.ph-аккаунт (`telegraph_access_token` в `bot_state`) и `file_id` картинок Инструкции остаются общими на весь бот: в них нет данных Пространства.

## Расписание и часовой пояс

Расписание и часовой пояс — свои у каждого Пространства: `schedule_settings.workspace_id`, `workspaces.timezone`. `week_label` считается в поясе Пространства. Сейчас пояс один — `APP_TIMEZONE`, он остаётся значением по умолчанию для новых Пространств. На экране Расписания появляется выбор пояса из российских (МСК−1 … МСК+9), без свободного ввода IANA-имени.

**Один тик вместо джоба APScheduler на Пространство.** Сейчас один `CronTrigger` в памяти плюс `reconcile_weekly_plan` на старте (#72) догоняет пропущенный запуск. Держать N cron-джобов в памяти и пересоздавать их при каждом изменении Расписания — это лишнее состояние, которое расходится с базой. Вместо этого один интервальный джоб раз в минуту. Он выбирает Пространства, у которых дедлайн этой недели (в их поясе) уже прошёл, нет активного Плана на неделю, нет `bot_blocked_at`, нет незавершённых Задач, сохранена Ниша и не идёт Онбординг. Последние два условия нужны, потому что `SettingsService` подставляет Нишу и Направления по умолчанию: без них тик в понедельник собрал бы План по чужой Нише каждому, кто нажал `/start` и ушёл, и сжёг бы его пробный План до «🚀 Запустить». Для каждого он вызывает `Plan.request_new`. Это ровно `reconcile_weekly_plan`, только по всем Пространствам и каждую минуту. Отдельная сверка при старте становится не нужна: первый тик после рестарта и есть сверка. Повтор безопасен, потому что ключ идемпотентности `generate_plan:{week}` уникален в пределах Пространства. Даже пустой результат (#84, План не создан) не запустит подбор снова в ту же неделю. Изменение Расписания на экране — просто запись в `schedule_settings`; `SettingsScreen` больше не зависит от `scheduler`.

Если Лимит Планов исчерпан, тик Задачу не ставит и один раз за неделю сообщает об этом Владельцу Пространства. «Один раз» помнит ключ `schedule_skipped:{week}` в `workspace_settings`. Неделю с этим ключом тик дальше не трогает вовсе (без блокировки строки Пространства каждую минуту), поэтому Лимит, поднятый `/admin limit` посреди недели, тик применит со следующей недели; в эту неделю План можно составить «🪄 Составить План».

## Защита от лавины: одна генерация за раз

- **Воркер выполняет не больше одной Задачи Пространства одновременно и обслуживает Пространства по кругу.** `claim_next` берёт `queued`-Задачу Пространства, у которого нет `running`-Задачи, в порядке `workspaces.last_job_claimed_at NULLS FIRST, jobs.run_at`, и обновляет `last_job_claimed_at`. Так в понедельник в 09:00 шесть Статей одного Пространства не заставят остальных ждать, пока все шесть допишутся: очередь чередует Пространства. Ограничение мягкое: при нескольких процессах-воркерах два из них могут на мгновение взять две Задачи одного Пространства. Это допустимо, потому что цель — честность очереди, а не инвариант. Общий параллелизм — число процессов-воркеров, как и сейчас.
- **Бот не ставит новую генерацию, пока у Пространства есть незавершённые Задачи.** Незавершённые — это `queued`/`running`, а также `done`/`failed`, чьё уведомление ещё не обработано (`notified_at IS NULL`). Проверка идёт под той же блокировкой строки Пространства, что и проверка Лимита (см. «Лимит»), поэтому два одновременных нажатия не проскочат её оба. Одно действие пользователя может поставить сразу несколько Задач («Утвердить всё» — Статьи и обложки по всем Темам), но следующее действие («✏️ Доработать», «🖼 Обложка», «Перегенерировать План», «✨ Предложить по Нише») получает «Дождитесь окончания текущей генерации». Тик Расписания такое Пространство просто пропускает до следующей минуты.
- **Суточный потолок Задач на Пространство** (`JOBS_PER_DAY_LIMIT`, по умолчанию 30) считается по `jobs.created_at` за последние 24 часа (индекс `(workspace_id, created_at)`, миграция 0015). Внутри него два своих потолка: Задачи, которые Лимит не тратят (Перегенерации Тем, обложки, анализ стиля #134), — `FREE_JOBS_PER_DAY_LIMIT`, по умолчанию 10, иначе «🔄» на Теме крутил бы платные вызовы модели до общего потолка; и `generate_plan` — не больше 5 в сутки, считая «Перегенерировать План» и повторные прогоны: каждый может пересобрать Карту Ниши (модель и запросы Wordstat из квоты, общей для всех Пространств, #128). Проверка знает тип Задачи: `Limits.reserve(workspace_id, job_type)`.
- **Известный компромисс: «🔁 Повторить» переиспользует ту же Задачу.** Её повтор проверяется по Лимиту и потолкам, но в суточные счётчики не добавляется (они считают созданные Задачи), а Лимит списывается только за успешный результат. Ограничение повторов — «одна генерация за раз» и `max_attempts` очереди.

## Учёт расхода

Учёт расхода — это `generation_steps` (#74), а не новая таблица. Она уже append-only. В ней уже есть по строке на каждый платный вызов, по каждой попытке Задачи, с провайдером, моделью, токенами и стоимостью. Стоимость `NULL`, если цена не настроена: незнание не превращается в 0. Вторая таблица с теми же строками дублировала бы запись и могла бы с ней разойтись. Добавляется:

- `workspace_id` — составной FK на `jobs`, пишется из `ClaimedJob.workspace_id` в `on_attempt` воркера;
- `unit TEXT NOT NULL` — `tokens` | `image` | `search_request` | `wordstat_request` и `quantity INT` (токены, 1 картинка, 1 запрос; `NULL`, если провайдер не вернул usage). Запросы Wordstat (`KeywordStats`) сейчас не пишутся вовсе. Они начинают писаться с `cost = NULL`, пока цена не настроена: их количество — главный сигнал злоупотребления подбором Направлений (упразднено #128, см. ADR-0016: теперь это Карта Ниши и недельная динамика `generate_plan`). Пишется только реальный запрос: попадание в кэш ничего не стоит и строкой не становится. Кэш переехал из `KeywordStats` в `generate_plan` (общий на процесс, по фразе и неделе — это публичная статистика, а не данные Пространства);
- триггер `BEFORE UPDATE OR DELETE ... RAISE EXCEPTION`, который делает неизменяемость свойством базы, а не только соглашением. `TRUNCATE` его не задевает, поэтому чистый лист в миграции работает.

Глобальный администратор видит расход как `SUM(cost)` и `SUM(quantity)` по `unit` за период. Если в периоде есть `cost IS NULL`, сумма помечается «неполная» — тот же принцип, что `JobCostSummary.complete`.

## Лимит

Лимит — пожизненный, не в неделю: это пробный доступ. Две независимые цифры: Планы и Статьи. По умолчанию `TRIAL_PLAN_LIMIT=1`, `TRIAL_ARTICLE_LIMIT=8` (решение Владельца проекта в #118): один План из 3 Тем на 2 Площадки — это 6 Статей, и ещё две «✏️ Доработать».

**Что списывается.**

- **План** — каждая `generate_plan`-Задача, давшая План хотя бы с одной Темой: по Расписанию, «🪄 Составить План», «🚀 Запустить» Онбординга, «Перегенерировать План». Пустой результат (#84) не списывается. План из одних предложенных вручную Тем (`/topic`) не списывается: генерации не было.
- **Статья** — каждая записанная Версия: первая генерация по «Утвердить всё» и каждая «✏️ Доработать». Перегенерация стоит столько же, сколько новая Статья (черновик + редактура; Исследование переиспользуется), поэтому она тоже списывается. Обложка, Исследование, Перегенерация Темы и подбор Направлений (упразднено #128, см. ADR-0016) Лимит не тратят. Их ограничивают суточный потолок и правило «одна генерация за раз».

**Когда.** Списание — по факту, при применении результата в обработчике уведомлений. Это та же транзакция, что `Plan.add_topics` / `Article.record_version`. Списание — строка в `limit_charges (job_id PK, workspace_id, unit 'plan'|'article', created_at)`, составной FK `(workspace_id, job_id) → jobs`. PK по `job_id` делает повторную доставку уведомления безвредной. Устаревший результат (`record_version` вернул `stale`: Статью уже перезапросили) не списывается — в Учёте расхода он остаётся. Так упавшая генерация не сжигает пробный доступ, а «🔁 Повторить» (та же Задача, тот же `job_id`) не требует возвратов и не списывает дважды. Списание фиксируется не позже `notified_at`: `mark_notified` вызывается только после успешного обработчика.

**Проверка — до постановки Задачи.** Одна функция в той же транзакции, что `enqueue`, под `SELECT … FROM workspaces WHERE id = $1 FOR NO KEY UPDATE` (не `FOR UPDATE`: тот задерживал бы `KEY SHARE` внешних ключей — вставки Задач, шагов Учёта расхода и списаний), по порядку: нет незавершённых Задач («Дождитесь окончания текущей генерации»), суточный потолок не достигнут, `списано + запрошено ≤ Лимит`. Отдельного счёта «в полёте» нет: первое условие гарантирует, что в момент проверки у Пространства нет ни одной Задачи без обработанного уведомления, а значит всё, что должно было списаться, уже списано. Блокировка строки Пространства сериализует два одновременных нажатия: второе увидит Задачи первого и получит «Дождитесь». Для этого `JobQueue.enqueue` принимает соединение вызывающего, а «Утвердить всё» (`approve_all` и постановка Статей и обложек) идёт одной транзакцией с проверкой — сейчас это отдельные вызовы через пул. «Запрошено» — число Задач, которые действительно будут поставлены: у «Утвердить всё» это все пары (Тема, Площадка) утверждаемого Плана — утверждение и постановка идут одной транзакцией, так что у уже утверждённого Плана все Статьи уже поставлены, и повторный callback ничего не ставит и не считает второй раз. Если не хватает, ничего не ставится, а ответ говорит, сколько Статей осталось, и предлагает убрать лишние Темы (🗑). Резервирование с последующим возвратом отвергли: оно требует компенсаций на каждом пути отказа.

**При исчерпании** кнопка отвечает: «Пробный лимит исчерпан: Планов X из X, Статей Y из Y». Дальше — контакт из `LIMIT_CONTACT` (например, @username Владельца проекта). Всё уже созданное остаётся доступно: История, Выгрузка, «📖 Читать». Главное меню показывает остаток строкой «Осталось: N План(ов), M Статей».

**Команда Глобального администратора.** `/admin` — список Пространств: id, @username, создано, последняя активность, Планы и Статьи «списано/Лимит», расход за 30 дней. `/admin limit <id> <планы> <статьи>` задаёт абсолютные значения (не больше 1 000 000), `/admin limit <id> default` возвращает Лимит по конфигу. `0 0` фактически блокирует Пространство. Команда видна в меню команд только Глобальному администратору. Остальным `/admin` отвечает как неизвестная команда. Глобальный администратор **не видит содержимого** чужих Пространств (Темы, Статьи, Настройки) — только метаданные и расход. Изменение Лимита пишется в лог с id администратора. Отдельный audit log — C5, вне этого решения.

## Безопасность

- **Callback с чужим id и устаревшая кнопка — один и тот же ответ.** Каждая ветка `CallbackDispatcher`, принимающая id (План, Тема, Статья, Версия, Задача, неделя Истории), первым делом резолвит объект через репозиторий с `workspace_id` нажавшего. «Не найдено» отвечает alert'ом «Кнопка устарела» — одинаково для «удалено», «чужое» и «не существует». Ответ не должен подсказывать, существует ли id у кого-то другого. Обычный пользователь не может нажать кнопку в чужом личном чате, но `callback_data` подделывается модифицированным клиентом, а пересланное сообщение может сохранить клавиатуру. Кнопки, отправленные до миграции, указывают на удалённые id и получают тот же ответ.
- **Задача чужого Пространства.** `retry` (`🔁 Повторить`) несёт `job_id`. `JobQueue.retry(workspace_id, job_id)` обновляет только `WHERE id = $1 AND workspace_id = $2` — сейчас это глобальный `UPDATE` по id. То же для `get_job`/`get_status`. Воркер читает Темы и Статьи для `regenerate_*` с `workspace_id` Задачи, поэтому payload со ссылкой на чужой id промахнётся, а не прочитает чужое. Уведомление доставляется только Владельцу Пространства, которому принадлежит Задача.
- **Данные одного Пространства не попадают в промпт другого.** Сейчас `Plan.recent_topic_titles` берёт заголовки *всех* Тем для проверки на повтор. После перехода это было бы и утечкой чужих Тем в промпт, и каналом injection из одного Пространства в другое. Метод получает `workspace_id`, как и чтение Настроек в каждом хендлере воркера. Это обязательный cross-tenant тест.
- **Prompt injection через Настройки** ограничен своим Пространством: текст Владельца попадает только в его собственные генерации. Что меняется: (1) у каждой Настройки, предложенной вручную Темы и комментария к Перегенерации появляется предел длины на вводе — сейчас он есть только у Аудитории (1000 символов). Ниша — 200, Направления — 20 строк по 100 (упразднено #128, см. ADR-0016), своя Персона — 1500, Проект — 500, Тема — 300, комментарий — 1000. Граница проверяется в `SettingsService`, а не в Telegram-слое. (2) Всё, кроме Персоны (ADR-0010), остаётся в зоне данных промпта. (3) Ссылки в тексте Статьи ставит только код: Проект и Источники, остальные вырезаются. Так что injection не превращает Страницу для чтения на общем telegra.ph-аккаунте бота в хостинг произвольных ссылок, кроме ссылки Проекта самого Владельца. `page_fetcher` уже пускает только на публичные IP.
- **Злоупотребление пробным Лимитом.** Одно Пространство на telegram id (`UNIQUE owner_telegram_id`). Повторный `/start` ничего нового не создаёт. «Одна генерация за раз» и суточный потолок Задач — см. выше. **Rate limit на `/start`**: не чаще одного раза в 3 секунды на telegram id (счётчик в памяти процесса бота — процесс один; лишнее молча игнорируется). Плюс глобальный потолок новых Пространств `SIGNUP_DAILY_LIMIT` (по умолчанию 50 за 24 часа, счёт по `workspaces.created_at`): сверх него `/start` отвечает «Регистрация временно закрыта», а Глобальный администратор получает одно уведомление в сутки. От фермы аккаунтов Telegram полностью это не защищает. Защищает то, что расход каждого такого Пространства ограничен Лимитом, а их число — потолком.
- **Заблокировавший бота.** На 403 Forbidden при доставке Пространство получает `bot_blocked_at`, уведомление считается доставленным (не тратит 5 повторов), тик Расписания его пропускает. Следующий `/start` сбрасывает отметку. Иначе брошенные пробные Пространства каждую неделю тратили бы деньги на Планы, которые никто не увидит.

## Миграция: чистый лист

`0012_personal_workspaces.sql` (следующий номер после `0011`) — **не** expand-шаг по ADR-0013: старый код с новой схемой не работает (`owner_settings` переименована, у `INSERT` нет `workspace_id NOT NULL`). Rolling deploy невозможен: выкатка — остановить `bot` и `worker`, `pg_dump`, поднять оба на новом образе. Чистый лист вместо backfill:

1. `TRUNCATE plans, plan_items, articles, article_versions, generation_steps, topic_research, jobs, pending_inputs, schedule_settings` — решение Владельца проекта (#118): текущие данные не переносятся. **Без `RESTART IDENTITY`**: последовательности `jobs.id` и `article_versions.id` продолжаются, поэтому `job_id` в кнопках старых сообщений («🔁 Повторить») не совпадёт с id новой Задачи. После этого `ADD COLUMN workspace_id BIGINT NOT NULL` проходит без значения по умолчанию.
2. `CREATE TABLE workspaces`, `workspace_settings`, `limit_charges`. Колонки, ключи, составные FK и индексы — по таблице выше. Триггер неизменяемости на `generation_steps`.
3. `ALTER TABLE owner_settings RENAME TO bot_state`; `DELETE FROM bot_state WHERE key NOT LIKE 'asset_file_id:%' AND key <> 'telegraph_access_token'` — пользовательские Настройки и флаг Онбординга уходят вместе с остальным.

`members`, `join_requests`, `join_request_broadcasts` в 0012 **не удаляются**: до PR Telegram ими ещё пользуется работающий бот. Их удаляет `0013_drop_roles.sql` (contract) в том же PR, где удаляется код.

**Промежуточное состояние (PR 1–3 плана).** Каждый PR в `master` оставляет бота рабочим. Пока Telegram-слой не переведён, `bot` и `worker` на старте берут одно «командное» Пространство: `Workspaces.get_or_create(owner_telegram_id=TELEGRAM_NOTIFY_CHAT_ID)`. Id группы отрицательный, поэтому не пересечётся ни с одним пользователем, а доставка на `owner_telegram_id` попадает в тот же чат команды, что и сегодня. Все вызовы получают `workspace_id` этого Пространства, а `Membership` по-прежнему решает, кто может действовать. Воркер перестаёт в ней нуждаться в PR очереди (берёт `workspace_id` из Задачи), бот — в PR Telegram. Поэтому PR Telegram, который удаляет `TELEGRAM_NOTIFY_CHAT_ID` из конфига, мержится только после PR очереди. Тик Расписания (свой PR, до Telegram) с первого дня работает по всем Пространствам: пока Пространство одно — командное, он ведёт себя как сегодняшний cron. Миграция 0013 ставит командному Пространству группы (`owner_telegram_id < 0`) `bot_blocked_at`: тик его не трогает, а данные, созданные в промежутке, не удаляются и видны Глобальному администратору. Если же `TELEGRAM_NOTIFY_CHAT_ID` был личным чатом Владельца (положительный id — id чата совпадает с id пользователя), это Пространство и становится его личным: остаётся незаблокированным, с данными. Сохранённые Направления 0013 удаляет: экрана для них больше нет (#128).

**Rollback.** 0013 откатывается пересозданием трёх таблиц из 0001 (пустыми). 0012 откатывается только восстановлением из бэкапа: данные удалены по решению Владельца проекта. Перед выкаткой — `pg_dump`, и он же — проверка на копии: восстановить дамп в отдельную базу, поднять на ней `bot` и `worker` нового образа (миграции применятся на старте) и убедиться, что оба стартуют без ошибок.

## Последствия

- Тесты на изоляцию обязательны в каждом PR плана (список — в плане). Gate потока C1 остаётся: ни одно Пространство не может прочитать, изменить, выгрузить или получить уведомление другого.
- `CONTEXT.md`: новые термины Пространство, Глобальный администратор, Лимит, Учёт расхода. Роль и Контент-менеджер помечены упразднёнными. План, Хаб, Онбординг, Инструкция, Главное меню переписаны под личку.
- Новые env: `GLOBAL_ADMIN_TELEGRAM_IDS` (через запятую), `TRIAL_PLAN_LIMIT`, `TRIAL_ARTICLE_LIMIT`, `JOBS_PER_DAY_LIMIT`, `FREE_JOBS_PER_DAY_LIMIT`, `SIGNUP_DAILY_LIMIT`, `LIMIT_CONTACT`. Удаляется `TELEGRAM_NOTIFY_CHAT_ID`; `.env.example` и README обновляются в PR Telegram.
- Вне решения: приглашения и общие Пространства, оплата и тарифы (C3), web-панель (C4), удаление и экспорт Пространства, audit log, RLS (C5).
