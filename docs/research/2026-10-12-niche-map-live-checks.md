## Итог для дизайна #128

1. **Один недельный `GetDynamics` даёт и тренд, и «год назад».** Запрос на 60 недель принят. Запрос с 2018-01-01 тоже принят (457 недель одним вызовом). Предела «5 лет» у API нет.
2. **Последняя полная неделя появляется не сразу.** В понедельник днём самая свежая точка — неделя, закончившаяся *позапрошлым* воскресеньем 04.10 (`2026-09-28`, то есть 28.09–04.10). Неделя 05.10–11.10 ещё не отдаётся. «Почему сейчас» должно брать последние точки ответа, а не считать их по календарю.
3. **`toDate` в будущем API молча обрезает до последней доступной недели.** `fromDate` не в понедельник даёт 400. Значит, достаточно выровнять `fromDate` на понедельник, а `toDate` можно ставить с запасом.
4. **`count` в Wordstat приходит строкой** (`"7300"`), `share` — числом. Нынешний `int(point["count"])` с этим справляется. Это нужно сохранить и для `GetTop`.
5. **`GetTop` по голой Нише почти не даёт вопросов** (0–2 из 50). Вопросы появляются, если в фразу добавить вопросительное слово: `«как ремонт квартиры»` дала 43 вопроса из 50. Шагу каскада «частый вопрос» нужен отдельный запрос `GetTop` с `«как <фраза Ниши>»`.
6. **Фильтр свежести в REST v2 называется `period`.** `PERIOD_2_WEEKS` работает. `resultsWithin` на верхнем уровне тела **молча игнорируется** (вложенный в `query` не проверяли): ответ 200, выдача та же, что без фильтра. API вообще не ругается на неизвестные поля, поэтому опечатка в имени поля не видна.
7. **Голая Ниша + `period` почти пуста.** `«психолог»` за 2 недели — «ничего не найдено», `«домашняя выпечка»` — 2 документа. С суффиксом «новости» те же Ниши дают сотни свежих новостей (`«психолог новости»` — 569, `«ремонт квартиры новости»` — 432). Инфоповоды искать запросом `«<фраза> новости»` + `period: PERIOD_2_WEEKS`, сортировка по релевантности.
8. **`SORT_MODE_BY_TIME` не использовать.** С `PERIOD_DAY` он отдаёт просто последние проиндексированные страницы со словом: YouTube, Avito, TikTok и даже порносайт, несмотря на `FAMILY_MODE_STRICT`.
9. **`region: "225"` принимается и работает.** С `225` выдача общероссийская (статьи «с чего начать ремонт»). С `2` — петербургские подрядчики. Невалидное значение (`"abc"`) **не даёт ошибку**: выдача тогда привязана к Калуге, видимо, по геолокации IP. То есть 200 ещё не доказывает, что поле применилось; доказывает разница выдач.
10. **`site:` и диапазон `date:A..B` в `queryText` работают.** `date:>YYYYMMDD` — нет («ничего не найдено»). Для свежести всё равно лучше `period`: это поле API, а не синтаксис запроса.
11. **429 не провоцировали.** Квоты по [лимитам](https://aistudio.yandex.ru/docs/ru/search-api/concepts/limits): Wordstat — 10 запросов/с и 100 запросов/ч, веб-поиск — 10/с и 10 000/ч. Как выглядит ответ на превышение, в документации не описано. Клиент Wordstat сейчас 429 не обрабатывает вообще: нужны `map_error` + `with_backoff_retry` (см. вопрос 1, «429»).

## 1. Wordstat: недельная динамика за ~60 недель

### Запросы

```http
POST https://searchapi.api.cloud.yandex.net/v2/wordstat/dynamics
Authorization: Api-Key <…>

{"phrase": "домашняя выпечка", "period": "PERIOD_WEEKLY",
 "fromDate": "2025-08-18T00:00:00Z", "toDate": "2026-10-11T00:00:00Z"}
```

| # | Фраза | Диапазон | Ответ |
|---|---|---|---|
| w1 | домашняя выпечка | 2025-08-18 (пн) … 2026-10-11 (вс), 60 недель | 200, 0,8 с, **59 точек**: 2025-08-18 … 2026-09-28 |
| w2 | ремонт квартиры | 2018-01-01 (пн) … 2026-10-11 | 200, 0,8 с, **457 точек**: 2018-01-01 … 2026-09-28 |
| w3 | психолог | `fromDate` 2025-08-20 (ср) | **400** `{"code": 3, "message": "rpc error: code = InvalidArgument desc = The from field value should be Monday"}` |
| w4 | психолог | 2025-08-18 … **2026-10-18** (будущее воскресенье) | 200, 0,35 с, 59 точек, последняя — 2026-09-28. Будущее молча обрезано |
| — | (пустое тело по ошибке скрипта) | — | 400 `phrase: Field is required / period: Field is required / from_date: Field is required`. `toDate` в списке обязательных нет, в [GetDynamics](https://aistudio.yandex.ru/docs/ru/search-api/api-ref/Wordstat/getDynamics) он тоже не помечен обязательным (без `toDate` не проверяли) |

### Ответ (обрезано)

```json
{"results": [
  {"date": "2025-08-18T00:00:00Z", "count": "7300", "share": 0.0003105380646422808},
  …
  {"date": "2026-04-06T00:00:00Z", "count": "26369", "share": 0.000996791387155088},
  …
  {"date": "2026-09-28T00:00:00Z", "count": "8800", "share": 0.00033979882365871566}
]}
```

- `date` — понедельник недели. `count` — строка (int64 в JSON), `share` — число (в документации — string).
- Заголовков rate-limit (`X-RateLimit-*`, `Retry-After`) в ответе 200 нет. Есть только `x-request-id` и `x-server-trace-id`.
- Ряд «домашней выпечки» показывает сезонность, которую месячная динамика размывает. Пасхальная неделя 2026-04-06 даёт 26 369 при обычных ~9–10 тыс. Майский провал — ~5,8 тыс.
- Пример расчёта на w1: среднее последних 4 недель = 8 532, предыдущих 4 = 7 565 (×1,13), те же 4 недели год назад (2025-09-08…09-29) = 7 780 (×1,10). Для «психолога» (w4): ×1,23 к прошлым 4 неделям, но ×0,97 год к году. Это сезонный рост сентября, а не тренд. Именно этот случай и должен отсеивать `yoy`.

### Вывод для пайплайна

- Один вызов `GetDynamics PERIOD_WEEKLY` на фразу за ~60 недель (или 2 года, если нужно «неделя через год вперёд» для `season_ahead`) — стоимость та же, 0,02 ₽.
- `fromDate` = понедельник ровно N недель назад. `toDate` = ближайшее воскресенье (можно в будущем). Последнюю неделю брать из `results[-1]`, а не из календаря. Отставание данных — **не меньше** ~8 дней: это одно наблюдение в понедельник днём. В какой день Wordstat публикует прошедшую неделю, неизвестно, так что отставание может доходить до ~14 дней.
- Кэшировать ряд по `(фраза, ISO-неделя запроса)`: неделя `results[-1]` известна только после запроса, поэтому ключом она быть не может. Внутри недели ряд почти наверняка не меняется (кроме дня публикации новой недели, он не проверен).

### 429

Не провоцировали. Что известно:
- Квота Wordstat — 100 запросов/ч и 10/с ([лимиты](https://aistudio.yandex.ru/docs/ru/search-api/concepts/limits)). Квоты поднимаются через техподдержку. На какой объект действует квота (каталог или облако), страница не уточняет.
- Ошибки Wordstat приходят в формате gRPC-gateway: `{"code": <grpc-код>, "message": "rpc error: code = …", "details": [RequestInfo]}`. Это видно по 400 выше (`code: 3` = InvalidArgument). По аналогии превышение квоты должно прийти как HTTP 429 с `code: 8` (ResourceExhausted). Это **вывод, а не наблюдение**. Ни страница [GetDynamics](https://aistudio.yandex.ru/docs/ru/search-api/api-ref/Wordstat/getDynamics), ни [лимиты](https://aistudio.yandex.ru/docs/ru/search-api/concepts/limits) коды ошибок не описывают.
- **Обработки 429 в клиенте Wordstat сейчас нет.** `KeywordStats` не вызывает `map_error`: и `keyword_dynamics` (`keyword_stats.py:153`), и `_fetch` для GetTop (`:191`) превращают любой не-200 в обычный `YandexError`, без `RateLimited` и без повтора. `keyword_stats` такую ошибку глотает, `keyword_dynamics` пробрасывает. Решение Владельца — 429 не должен ронять План. Значит, Карте Ниши нужен `map_error` + `with_backoff_retry` в `KeywordStats` со своей задержкой и кэш.
- `WebSearch` вызывает `map_error`, но без `with_backoff_retry`: 429 веб-поиска сразу становится исключением.
- `map_error` в `_resilience.py` читает `retryAfter` из тела 429. Ни в документации, ни в ответах такого поля не видно, заголовков rate-limit в 200 тоже нет. Время ожидания при 429 придётся задавать самим (окно квоты — час).
- Чтобы 429 «увидеть» безопасно: залогировать полный статус и тело первого же 429 в проде. Сейчас `keyword_dynamics` кладёт тело в текст ошибки (`:155`), а GetTop (`_fetch`, `:192`) — только `status`.

## 2. Wordstat GetTop: вопросы и ассоциации (`numPhrases: 50`)

```http
POST https://searchapi.api.cloud.yandex.net/v2/wordstat/topRequests
{"phrase": "домашняя выпечка", "numPhrases": 50}
```

Ответ: `{"totalCount": "37305", "results": [{"phrase": "…", "count": "37305"}, …], "associations": [{"phrase": "…", "count": "…"}, …]}`. Все счётчики — строки.

| Фраза | `results` | Вопросов в `results`* | `associations` | Примеры ассоциаций |
|---|---|---|---|---|
| домашняя выпечка | 50 | 0 | 18 | что испечь (91 912), что можно испечь, что испечь к чаю, торт дома |
| ремонт квартиры | 50 | 2 | 16 | отделка дома (207 186), ремонтные работы, отделочные работы |
| психолог | 50 | 2 (мусорные: «психолог ли») | 19 | психология это, психологическая помощь, бесплатная психологическая помощь |
| **как** ремонт квартиры | 50 | **43** | 16 (те же, что у «ремонт квартиры») | — |

\* Вопросом считали фразу с «как/что/почему/сколько/где/можно/нужно/ли…».

Вывод:
- Хвост `results` у голой Ниши — коммерческие и навигационные фразы («ремонт однокомнатной квартиры», «психолог ирина»), а не вопросы.
- Для шага «частый вопрос» делать отдельный `GetTop` по `«как <фраза>»` (и, может быть, `«что <фраза>»`). Это +1–2 запроса Wordstat на фразу Карты Ниши при перестройке раз в месяц.
- `associations` хороши для расширения Карты Ниши смежными запросами. Они не зависят от вопросительного префикса. Документация обещает до 20, получили 16–19.

## 3. Веб-поиск: фильтр свежести и `region`

Базовое тело совпадает с `WebSearch.search` (только `groupsOnPage: "10"`):

| s13 | «**ремонт квартиры новости**», `PERIOD_2_WEEKS` | 432 | vesti.ru, aif.ru, ura.news, rbc, kp.ru, 28.09–10.10 |

Наблюдения:
- В XML каждого документа есть `<modtime>` (`20261010T080745`). Это время индексации/изменения, а не публикации: страница Pikabu «01.10.26» пришла с `modtime` 12.10. Для «почему сейчас» дату новости лучше не выводить из `modtime`, а писать «за последние 2 недели».
- Описание `period` в [WebSearch.search](https://aistudio.yandex.ru/docs/ru/search-api/api-ref/WebSearch/search): `PERIOD_DAY`, `PERIOD_2_WEEKS`, `PERIOD_MONTH`, `PERIOD_ALL_TIME`. [Страница-концепция](https://aistudio.yandex.ru/docs/ru/search-api/concepts/web-search) называет фильтр `resultsWithin`/`results_within`, то есть документация сама себе противоречит. Наблюдение: `resultsWithin` на верхнем уровне тела молча игнорируется (s3). Вложенный `query.resultsWithin` не проверяли. Вывод: используем документированное и проверенное `period`.
- В свежих новостях встречается мат в заголовке (s15, Дзен). Решение Владельца «новости любые» требует хотя бы фильтра на стороне LLM, если заголовок новости показывается пользователю.

Вывод для пайплайна:
- Инфоповоды: `queryText = "<фраза Карты Ниши> новости"`, `period: "PERIOD_2_WEEKS"`, сортировка по релевантности (без `sortSpec`), `region: "225"`. Пустой ответ (XML error 15) — нормальный исход: каскад идёт дальше.
- `region` оставить `"225"`. Если потом появится регион Пространства (открытый вопрос 2 исследования), подставлять ID региона Яндекса. Валидировать его самим: API невалидное значение не отклоняет.
- Тест на тело запроса (имена полей) обязателен: API не отклоняет неизвестные поля.

## Ошибки веб-поиска и квоты (по документации)

- Квоты синхронного поиска: 10 000 запросов/ч, 10/с ([лимиты](https://aistudio.yandex.ru/docs/ru/search-api/concepts/limits)). Для Плана это не узкое место.
- [Коды ошибок Search API](https://aistudio.yandex.ru/docs/ru/search-api/reference/error-codes.html) приходят XML-тегом `<error code="…">`. Среди них **32** — превышен суточный лимит и **55** — превышен лимит в секунду. Наблюдение: в наших вызовах XML-ошибка 15 пришла с HTTP 200. Вывод (не проверено): превышение лимита веб-поиска тоже может прийти как 200 + `<error code="55">`, а может и как HTTP 429. В первом случае `parse_search_xml` превратит его в общий `YandexError`, во втором `map_error` даст `RateLimited`. Повтора нет ни там, ни там. Для каскада инфоповодов: **XML 32/55 и HTTP 429 → «нет новостей сейчас»**, а не падение Плана.

## Что осталось непроверенным

- Реальный вид HTTP-ответа Wordstat на превышение квоты (сознательно не провоцировали).
- `GetDynamics` без `toDate`; `PERIOD_DAILY`; `regions[]` в Wordstat.
- В какой день недели Wordstat публикует данные за прошедшую неделю (видели одну точку: в понедельник днём недели 05.10–11.10 ещё нет).
- Вложенный `query.resultsWithin` в веб-поиске.
- Как приходит превышение лимита веб-поиска: XML 32/55 в HTTP 200 или HTTP 429.
- Эмбеддинги (п. 5 исследования) и отложенный веб-поиск (п. 7).
